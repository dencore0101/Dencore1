PHASE 12 — PATIENT BENEFITS + ADVANCED CLINICAL FOLLOW-UP SYSTEM

IMPORTANT:
Phases 0–11 are already completed. Do NOT rebuild, reset, or redesign the existing application.

Inspect the current production code first. Add Phase 12 as an additive feature while preserving all existing functionality, database data, UI, authentication, RLS, billing, appointments, patient profiles, timeline, reports, and Hostinger/Supabase deployment architecture.

DO NOT add Consent Management in this phase.

Phase 12 consists of:
PART A — Generic Patient Benefits Engine
PART B — Advanced Clinical Follow-up & Reminder System

The clinic owner has very little time for future development, so ordinary configuration must be possible from the application UI without editing code or requiring another Bolt session.

==================================================
PART A — GENERIC PATIENT BENEFITS ENGINE
==================================================

1. PURPOSE

Create a completely configurable Patient Benefits system.

The first use case is a Free Scaling Benefit, but do NOT hardcode scaling into the system.

The system must eventually support:
- Free Scaling
- Free Consultation
- Free Check-up
- Free IOPA/RVG
- Free Polishing
- Free Procedure
- Percentage Discount
- Fixed Amount Discount
- Implant maintenance
- Custom Benefit

The clinic owner must be able to create, edit, activate, deactivate and manage benefits entirely from the UI.

2. MAIN NAVIGATION

Add a new main module:

Patient Benefits

Subsections:
- Overview
- Benefit Programs
- Eligible Patients
- Redemptions

- Settings

Do not create a separate hardcoded "Scaling Bonus" module.

5. ELIGIBILITY RULES

Configurable minimum amount.

Calculation basis:
- Treatment amount before discount
- Treatment amount after discount
- Amount actually paid
- Amount invoiced

Recommended default:

The clinic owner can change it.

Eligible procedures:
- All procedures
- Selected procedures

Eligible categories:
- All categories
- Selected categories

Example:
Any treatment above ₹10,000 qualifies.
Or:
Only prosthetic treatments above ₹15,000 qualify.
Or:
Only RCT + crown packages qualify.

Do not hardcode eligibility around one treatment.

6. PAYMENT/COMPLETION CONDITION

Allow configuration of when the benefit becomes active.

Options:
- When treatment is accepted
- When treatment is completed
- When full qualifying amount is paid
- When configured percentage is paid
- Custom clinic rule if practical

Do not automatically grant a large benefit merely because a high-value treatment was quoted.

10. REDEMPTION

When a patient uses a benefit:
1. Verify benefit is active.
2. Verify current date is within validity.
3. Verify an unused entitlement exists.
4. Create redemption record.
5. Link redemption to procedure.
6. Link to treatment where applicable.
7. Link to visit.
8. Link to appointment where applicable.
9. Mark entitlement as redeemed.
10. Add event to patient timeline.

Do NOT create a fake negative payment.

A free procedure should be recorded as a benefit-covered procedure/redemption with ₹0 patient charge where appropriate.

Do not corrupt revenue or payment reports.

11. REVERSE REDEMPTION

- Add audit event.

35. REMINDER ENGINE

Implement a reliable reminder state machine:

Follow-up created
↓
Calculate reminder dates
↓
Reminder becomes due
↓
Is follow-up still active?
↓
YES → prepare/send reminder
NO → cancel reminder
↓
Next reminder
↓
Follow-up date
↓
Completed?
YES → stop
NO → overdue/no-show workflow

Critical behavior:

If a follow-up is:
- Completed
- Cancelled
- Rescheduled

then all obsolete future reminders must stop.

If rescheduled:
1. Cancel old reminders.
2. Update follow-up date/time.
3. Generate new reminder schedule.
4. Preserve original history.

Never send a reminder for the old date after rescheduling.

36. REMINDER SENDING ARCHITECTURE
